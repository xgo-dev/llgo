# layoutlint field accesses

This standalone Go tool checks direct struct-field offsets, actual address alignment, scalar loads/stores, struct array strides and five ABI type-header properties against a Go baseline. It also checks that each observed stride agrees with LLGo's size metadata. It uses the repository's existing `github.com/goplus/gogen` dependency to generate access wrappers, and native LLDB to observe their pointers and memory.

```sh
go build -o /tmp/layoutlint ./chore/layoutlint
/tmp/layoutlint -root /path/to/module -output /tmp/wrappers ./some/package
/tmp/layoutlint -root /path/to/module -test ./some/package
```

Inputs are Go package patterns or selected Go files. With no positional input the package is `.`. `-test` includes test-file declarations and builds a test executable; library packages require it. The output must be a new directory; omitting it creates a temporary directory. Artifacts are grouped by import path. Set `LLGO` to the compiler executable and `LLGO_LLDB` to the native `lldb` executable when they are not on PATH. Configure LLVM and `LLGO_ROOT` as required by that compiler. Go and LLGo must target the same native platform.

Input packages are listed first, then loaded and checked individually. A load or observation failure is retained and makes the final exit status nonzero, but does not prevent later inputs from being checked. Inputs without eligible concrete struct types print SKIP after type discovery, without observation builds or LLDB. Ordinary empty structs still receive size, stride and metadata checks.

Discovery includes package-level concrete declarations and concrete generic instances recorded by Go's type checker, including instances reached through field types. For example, `Data[int]` is checked without requiring a `type DataInt = Data[int]` alias. Identical types are deduplicated. Generic declarations with free type parameters are templates, not concrete observation subjects; the tool does not invent type arguments or lift local type declarations. Informational exclusions use a format distinct from compiler errors. PASS reports counts of concrete structs, field accesses, owner-package observations and metadata field offsets rather than implying coverage of every declaration.

For each accessible, non-blank field of a package-level concrete struct declaration whose underlying type is neither an array nor a struct, generation produces `layoutRead_Type_Field(p *Type) FieldType` and `layoutWrite_Type_Field(p *Type, v FieldType)`. Each wrapper first takes `field := &p.Field`, passes the object pointer, field pointer and access ID to a private noinline checkpoint, then reads or writes through that same field pointer. Scalar wrappers also stop after the access: a reader exposes the address of its loaded value, and a writer exposes the field address again. Array and inline struct fields instead expose their addresses directly from the existing init; they are never passed, returned or assigned as whole values by the generated checks. The LLGo wrappers do not compute offsets or query reflection, `unsafe.Sizeof`, or `unsafe.Offsetof`.

Each input package gets its own gogen package, reusing its loaded `types.Package` and source file set. Field addresses are typed AST expressions supplied through `gogen.Element`; gogen handles signatures, references and imports. Source overlays add the generated file without editing the input or copying its module. A generated init first retains and exposes each eligible struct's type descriptor, exposes two array-element addresses per type, observes direct aggregate fields, nested inline field paths and the first two elements at each struct-array dimension, invokes scalar wrappers at two addresses and other wrappers once, then exits before the original main or tests execute. This is a fixed set of calls determined by source types, independent of loops in the original input. Dependency initialization and any preceding package init functions still execute. The checkpoint prints its primitive arguments to keep the call observable; its output is not measurement data. LLDB launches with `--no-stdio` so debugger commands cannot be forwarded to the target's terminal input.

The baseline is obtained from Go ABI type descriptors and their relocations in the `go tool compile -S -S` data listing, using the original package's compiled Go files and an importcfg assembled from Go dependency archives. When a storage model is needed, gogen's `NewTypeDefs`, `InitType` and `WriteTo` generate its complete declarations and imports in a Go-only `go-models.go`; layoutlint does not render those types through `types.TypeString` or assemble their imports itself. A separate `go-references.go` contains named interface globals initialized from typed nil pointers to retain the original and model descriptors. These files are compiled together with the original package without linking or executing it. StructField.Offset supplies field offsets, each field type's Size_ supplies its width, Align_ supplies object/array-element alignment, and FieldAlign_ supplies alignment when a type occurs as a struct field. ArrayType.Elem supplies the element descriptor, whose Size_ determines the expected index spacing. Basic descriptors are read from Go's runtime compiler listing; imported named descriptors are read from their defining packages, with dependency listings reused across inputs. No Sizeof, Alignof or Offsetof constants or asmhdr macros are generated or parsed. Scalar constants and their expected native bytes are constructed by the Go tool itself. The tool and both compilers must target the same native architecture.

Only the Go storage baseline replaces ordinary function values with `struct { code uintptr; env unsafe.Pointer }`. This models two target words, including when env is nil; it is not a hardcoded 16-byte size. The replacement recurses through inline structs and arrays, including named function types and aliases. Pointer, slice, map, channel and interface headers remain unchanged, and types without inline function values keep their original Go baseline. Go compiles the resulting model to determine offsets, alignment, trailing padding, size and PtrBytes; layoutlint does not add guessed byte deltas. Embedded model fields retain their direct names and positions as explicit fields, without inheriting method sets. The original source and LLGo access wrappers still use the original types. Native declarations marked `llgo:cdecl`, `llgo:stdcall` or `llgo:type C` are not expanded by this rule.

For example, `struct { F func(); Tail uint64 }` has an original Go size of 16 on a 64-bit target. The Go-compiled storage model has Tail at offset 16 and total size 24. Field access checks, scalar buffer sizing, array stride checks and storage metadata checks all use that model. Original Go metadata remains in `go.type_header` and `go.pointer_header`; `go.layout` contains only the storage type symbol, size, PtrBytes and alignment requirements. A synthetic struct's Kind, name, flags or comparability never replaces the original function's semantic metadata.

The Go compiler output is streamed directly to `go-compile.log`. A line reader extracts type data, GC bitmaps and the named reference globals, while ignoring instruction bodies. Each reference global's relocation identifies a pointer descriptor; its Elem relocation identifies the original type or its storage model. This works for aliases without reconstructing the compiler's anonymous-type symbol names. The parser preserves implicit zero tails and ignores zero-width `R_USEIFACE` markers when resolving pointer fields. An unlinked zero word with an address relocation is retained as a symbolic reference, not treated as nil. An imported alias such as `type V = reflect.Value` resolves its descriptor from the defining package's Go compiler listing; those dependency builds are reused within the invocation. Missing reference globals or unresolved required definitions fail the baseline. `go-abi.json` preserves extracted symbols' complete bytes and relocations, including struct-field data beyond the common header.

LLDB stops at the checkpoint's function entry before its prologue. On Windows/386, both MSVC and MinGW place the three parameters in four-byte stack slots at ESP+4, ESP+8 and ESP+12; the checker reads ESP and those raw bytes. Other supported native targets use the generic argument registers `arg1`, `arg2` and `arg3`. The checker verifies the expected access ID, subtracts the object address from the field address outside the debuggee and compares the result with Go. It also checks that each address is divisible by its Go alignment requirement. A misaligned object or field fails the package before the pending access executes. Commands are sent one at a time by Go. Startup executes `process launch --no-stdio` from `launch.lldb` through `command source --stop-on-continue false --stop-on-error true`, which makes launch synchronous. LLDB consumes the initial loader stop and resumes to the first checkpoint; the controller does not request a stop at the program entry. Subsequent `process continue --continue-to-bkpt 1` commands wait synchronously for the next stop before arguments are read. Debugger type layouts and language-level expressions are not used. Missing or unexpected observations, debugger errors and unsuccessful process exits fail the check. The debugger must support this synchronous command and the target-specific register/memory reads.

A synchronous launch or continue can also return on a signal or exception. Before reading any arguments, the controller checks all thread stop reasons, requires one thread at the requested breakpoint, and verifies its PC against the resolved breakpoint entry address and hit count. It selects that thread when necessary. Stops in a loader, exception dispatcher or unrelated function cannot supply layout observations. On Linux, LLDB passes Boehm's SIGPWR/SIGXCPU suspend/restart signals and LLGo's SIGURG thread-snapshot signal without stopping or suppressing delivery. Other signals and exceptions remain errors. macOS and Windows use the same checkpoint validation, without inheriting the Linux signal policy.

Boolean, integer (including `uintptr`), floating-point and complex fields also get a load/store check, including named types and aliases with those underlying types:

- Storage is a `uint64` array containing space for the Go struct size, at least 16 guard bytes on each side and room for address placement. It contains no declared pointer fields for the GC to follow while LLDB seeds it with bytes. If the Go object alignment is `A`, address case 0 rounds up a pointer inside the buffer to a multiple of `2*A`; address case 1 adds `A` to that pointer. Both addresses satisfy Go, but the second is not aligned to `2*A`. LLDB verifies the actual remainder for both cases before injecting bytes, so a misplaced test address cannot silently pass. Each address gets its own read and write checks and independently seeded memory.
- Before an access, the checker verifies that the observed field address plus the Go field width fits inside this buffer. An out-of-range access fails that package immediately, while the target is still stopped. Earlier results remain in the report; later accesses stay unobserved. Other input packages are still checked.
- For a load, LLDB fills the buffer with a known pattern and puts the expected scalar bytes at the Go field offset. After the load, LLDB reads the result's raw bytes and checks that the source buffer is unchanged.
- For a store, LLDB puts the complement of the expected bytes in the field. The wrapper stores a known typed constant. LLDB then reads the complete buffer and verifies the field bytes, neighboring bytes and guards. The check never uses an LLGo field read to verify a store.

Each scalar currently uses one nonzero pattern; this is not an exhaustive test of scalar values. For example, a store to `point.x` that also overwrites `point.y` fails even when the bytes of `point.x` are correct. Guard checks cover the captured buffer; they do not prove the exact machine instruction width or detect every out-of-range read. A load is observed through its result's storage before return, so this does not test its return-value ABI.

For example, the existing `u64parts` struct in `cl/_testrt/float2any` contains two `uint32` fields and has Go alignment 4. Addresses ending in `0x90` and `0x94` exercise both eight-byte alignment and four-byte alignment without eight-byte alignment. Both must preserve the same Go field offsets and read/write results. These are addresses of the original type, not new handwritten input cases.

Same-package private fields follow the same wrapper or address-probe rules as public fields. CGo-generated C typedefs and blank type declarations are not observation subjects; ordinary Go structs containing fields such as C.int remain eligible. CGo's processed user source is identified through its original file references. For the Go baseline, cached support files are copied under `_cgo_*.go` names and processed user source gets ordinary `.go` names, preserving both directive validation and the ability to declare methods on local Go types. Compiled imports supply the implicit syscall/runtime/cgo archives. No CGo source contents are rewritten or removed. Arrays and inline structs, including named types, aliases, anonymous structs and embedded structs, retain their full types and array lengths but receive address observations instead of whole-value copies. This avoids copying a large array indirectly through a containing struct as well. Special ABI declarations (`llgo:cdecl`, `llgo:stdcall`, `llgo:type C`) remain excluded. Access wrappers copy function values using their original types; only the Go storage baseline uses the two-word model.

For inline dependency types with private fields, gogen emits additional private probes in their defining packages through source overlays. For example, a test package observes the placement of `strings.Builder`, while a generated file in `package strings` observes `Builder.addr` and `Builder.buf`. The probes expose actual parent/field addresses and use a private generic helper to measure `[2]F` strides without naming foreign private field types. They do not perform injected load/store tests. LLGo replacement packages receive the same address-probe source in the replacement directory reported by the compiler's environment; that query supplies only source locations, never expected layout facts. Dependency checkpoints have distinct IDs and are matched independently of package initialization order. Missing or duplicate checkpoints fail the input.

The defining package's Go baseline uses `go build` with a source overlay so cmd/go supplies assembly ABI information when needed, as for `reflect`. It retains type descriptors through the same reference globals and reads the same ABI fields as ordinary input packages; it generates no offset, alignment or width constants. Ordinary input packages retain the direct `go tool compile` path. No Go executable is run and no offsets are guessed. Dependency observations and their source annotations are retained under `private_layouts` on failure, and removed when the input passes.

Metadata retention uses a typed nil `*T` converted to an empty interface. The init extracts the interface's type pointer and passes it to the existing checkpoint. This requests the `*T` descriptor and its referenced `T` descriptor without constructing a value of T. No reflection getter or new wrapper function is generated. Empty structs are retained and inspected even when there are no field-access wrappers.

At the metadata checkpoint, LLDB locates the `*T` global by its actual address, reads its bytes and follows `PtrType.Elem` to T. Both addresses must identify readable symbol ranges; nil or missing descriptors fail the package rather than count as uncovered or passing. Reads happen after the loader has resolved runtime addresses. The decoder uses LLGo's native 32/64-bit `runtime/abi.Type` wire layout; its fixed descriptor-header length is distinct from `Size_`, which describes values of T. It does not use DWARF type layouts or LLGo reflection to decode that header. The two words in this header's `Equal` field follow that specific ABI field's format and do not impose a representation on other function values.

This metadata stage validates retention and captures both compilers' raw common headers. It records Size_, PtrBytes, Hash, TFlag, alignment, kind, Equal, GCData, the string/name reference and PtrToThis for both `*T` and T. Each report entry's `go` member contains the Go headers and symbolic relocations, alongside the LLGo headers read through LLDB.

For each captured T, Size_, PtrBytes, Align_ and FieldAlign_ must equal `go.layout`, including the two-word closure model when applicable. For `*T`, these properties must equal the original Go pointer header: enlarging T does not enlarge a pointer to it. Kind is compared with the original Go type or pointer header after decoding the low five bits, so LLGo's separate DirectIface/GC flag bits do not create a false kind mismatch. The original Go and LLGo headers are never rewritten to normalize a difference. A mismatch fails the package, while subsequent valid metadata and memory observations continue to be collected. A missing descriptor or an invalid kind that prevents following the capture path remains an error; differences in already-read headers are retained before returning that error.

The report's `metadata[].differences` entries identify `descriptor` (`type` or `pointer`), the ABI `field`, and numeric `expected`/`actual` values. The containing metadata entry supplies the source type and location. For example, a closure-containing struct can have the correct size and field accesses but still fail with `metadata.PtrBytes: expected 16, got 0`. An empty differences list only covers these five header properties, and does not imply success if the metadata entry was not observed or the report contains a capture error. Hash, TFlag, Equal, GCData, names and PtrToThis are recorded but not compared in this stage.

The same metadata stop compares every direct field-table offset of each retained struct, including private and blank fields, with the Go compiler's corresponding field table. Entries are paired by declaration index, so repeated blank names are unambiguous. A blank field has no direct read/write or address probe; its metadata offset, the containing size and surrounding observable fields are still checked. Nested access paths follow field type references; array paths follow `ArrayType.Elem` and check the array length. Each descriptor and field table is read once per root capture and reused for repeated paths, including the two sampled array indices. Missing or unreadable tables, mismatched descriptor kinds or field counts, and mismatched array lengths fail capture.

At each existing direct or nested field offset check, the controller requires `GoOffset == LLGoOffset == MetadataOffset`. The first is the compiled Go storage baseline, the second is the actual address difference, and the third is the field table's Offset value. `metadata_offset` in the corresponding JSON observation preserves that third value; it is absent for array-element rows, which are not struct fields, and for field observations whose metadata could not be captured. Thus a correct field access still fails if reflection's field table records the wrong offset. The raw descriptor and field-table reads remain in `metadata-N-layout-M*.bin`. This step does not compare field names, tags, embedded flags, or the complete identities/headers of leaf field types. Function type references remain leaves, so a public function descriptor's size is not substituted for its two-word physical storage.

For every eligible T, the existing init declares `var layoutItemsN [2]T` and passes `&layoutItemsN[0]` and `&layoutItemsN[1]` to the same checkpoint. The controller subtracts the two observed addresses and compares the stride independently with the Go storage baseline's Size_ and LLGo's T descriptor Size_. Either mismatch fails the command. This observes the space the compiled array indexing assigns to each element, including trailing padding; it does not use LLGo Sizeof or infer object size from allocator boundaries. Empty structs are included and compared with the Go size of zero. Each type adds one checkpoint and storage for two elements, with no expansion of nested arrays or additional wrapper functions. For example, fields at offsets 0 and 4 can pass individual accesses while an incorrect stride of 12 disagrees with Go's total size of 8.

Each metadata entry's `stride` object records the first and second element addresses, their difference in `bytes`, `go_matches` and `metadata_matches`. The compared sizes are in `go.layout.size` and `type_header.size`; `go.type_header.size` retains the original Go representation. A missing stride object means the observation was not reached, not that it passed. Missing or unexpected checkpoints fail the command.

Field sizes are also measured independently. For each distinct field type F selected by the direct or recursive checks, gogen emits `[2]F` in the existing init and passes the two element addresses to the existing checkpoint. Identical field types share one measurement. LLDB subtracts the addresses and compares the stride with Size_ from the corresponding Go field-type descriptor, including the closure storage model. No LLGo Sizeof, metadata size or gap between neighboring struct fields is used as the actual field size. The `size` object on each field observation records the expected/actual sizes, capture status and both addresses. A mismatch fails the command. These probes do not expand array elements, but storage for two values still scales with the size of F.

Before descending a field path, the generator resolves aliases and inspects the Go underlying type. Inline structs, including anonymous structs and named aliases, recurse through their accessible non-blank fields. Pointers, slices, maps, channels, interfaces and function values end the traversal. For example, `Outer.Inner.Value` observes the address of Inner and the address of its Value field, and compares their difference with StructField.Offset in the Go descriptor for Inner. Both addresses must meet the Go descriptor's alignment requirement for their occurrence: Align_ for a root or array element, FieldAlign_ for a struct field. Different occurrences of the same type retain their own address checks. Recursion through pointer types is never followed, and the closure storage model does not introduce synthetic code/env observations into the original LLGo type.

Arrays whose eventual element is a struct receive observations for indices 0 and 1 at each dimension, followed by the same recursive field checks. Each element's address is checked relative to its array base against `index * Go element size`; offsets 0 and one element size also verify the first element spacing. Named and aliased arrays/elements are included. The Go descriptor traversal uses the storage model when closure fields affect layout. For example, `arr2 [3]E` with `E struct { i int }` adds four element-path checkpoints beyond the array field's own address observation: `arr2[0]`, `arr2[0].i`, `arr2[1]`, and `arr2[1].i`. A length of 4096 produces the same four element-path observations. Length-one arrays only inspect index 0; length-zero arrays generate no element subscripts. Zero-sized elements can have expected spacing zero. Multidimensional arrays sample combinations of their first two indices; they never iterate each dimension's full length. Arrays whose eventual element is a scalar or pointer receive no element observations, but their field offset, alignment and full field size are still checked.

Paths without array indices, including direct array and struct fields, are recorded under `nested_fields`; paths through arrays remain under `array_elements`. Both use the existing offset and alignment result format. `array-element` offsets are relative to the immediate array base; `nested-field` and `array-field` offsets are relative to the immediate containing struct. Thus `Rows[1].Inner.Value` reports Value's offset within Inner, while earlier path observations check Inner's placement. MetadataOffset uses that same immediate containing struct. These checks reuse the existing `[2]T` storage and checkpoint function without allocating another object or adding wrapper functions. They do not add nested value load/store checks. Removing whole-value copies does not shrink the measured types: `[2]T` and `[2]F` storage, and scalar buffer scans for a struct containing a large array, can still cost time and memory proportional to array size.

Only failed inputs retain diagnostic artifacts. A successful input prints PASS, does not write `offsets.json` or annotated source, and removes its temporary build/debug files. Empty package directories may remain; failures belonging to other input packages are preserved. On failure, the output retains generated source, the Go-only reference globals and storage models, `go-abi.json`, the reference object and importcfg, the LLGo executable, the source overlay, LLDB commands, build/debug logs and `offsets.json`. Scalar checks additionally retain seed, before/after memory and loaded-value binary files per observation. JSON records source locations, operation, address case, expected/actual offset and whether the access was observed. Its `alignment` object records the Go requirements, actual object/field addresses and alignment checks; its `access` object records expected/actual bytes, value and memory comparisons, and unexpected byte offsets relative to the struct base (negative offsets are in the leading guard). Non-scalar observations have only address case 0 and do not require double alignment. The report's `metadata` entries retain symbol names, addresses, raw/decoded common headers, capture status and header differences; `metadata-N-pointer.bin` also includes the Elem reference, while `metadata-N-type.bin` contains T's common header. The LLDB command transcript contains addresses from that run, so it is not a replay script. Offset, size, address alignment, access, stride or metadata differences fail the command, including intentional representation differences that have not been assigned a separate comparison rule.

After a failure with a Go baseline, `annotated/` contains copies of the relevant input sources. Field declaration lines show `GoOffset: <offset> GoSize: <bytes> LLGoOffset: <offset> LLGoSize: <bytes> MetadataOffset: <offset>`, followed by a failure reason when the observed values disagree. Offsets use the same immediate-parent convention as JSON; array paths identify the sampled element. Array-element observations omit MetadataOffset because they have no StructField entry. Repeated identical observations are combined, while different paths or results on one line retain their labels. Struct declaration lines show total size and any ABI header differences. Unreached observations explicitly say `unobserved`; zero is never used as a substitute. Existing line numbers and comments are preserved. The Go values refer to the approved storage baseline, so an ordinary function field has two-word size here.

Load/store failures are annotated on the actual `value := *field` or `*field = v` statement in a copy of the generated wrapper. Comments identify the address case, expected/actual bytes and unexpected memory changes. They are not attached to original program accesses, which this tool does not execute. Sources loaded for owner-package probes are included in the annotated copies; other dependency declarations remain represented in JSON. Original input files and the generated source used for compilation are never edited by annotation rendering.

This stage checks generated accesses at O0. Non-scalar fields retain offset and actual address alignment checks on zero-valued typed storage; they do not receive injected byte patterns. It does not inspect LLVM IR or validate LLVM alignment annotations, metadata beyond the five common-header properties and the field-path checks described above, all allocation sites or every instruction of the original program. Nested address checks stop at pointer/container boundaries and at the array sampling limits described above.

## CI integration

The LLGo workflow invokes `.github/actions/check-layout` on its ten existing native combinations: Linux amd64/arm64, macOS amd64/arm64, and Windows amd64/arm64/386 with both MSVC and MinGW. The main compiler jobs reuse the core test runner's selected package list and dependency versions. Linux ARM64 and Intel macOS check the native regression packages already exercised by their jobs. All ten combinations additionally check the disjoint compiler fixture directories (`cl/_test*/*`) and runtime fixture directories (`runtime/_test/codegen/*`). Python fixtures (`cl/_testpy`) are excluded from layoutlint; their existing compiler tests remain unchanged. Windows also excludes `cl/_testlibc/once`, matching the original compiler runner's pthread restriction. These choices belong to the CI caller, not layoutlint's generic package loader. Compiler fixtures use `-test` so main packages and library packages can both produce observation executables. Each input is selected once per combination; layoutlint is not also attached to Go-version shards, bootstrap, development, release, cross-compilation, Wasm or embedded jobs.

The shared action takes `llgo`, `artifact-name`, and `args` (one literal existing command argument per line), with an optional `source-root` defaulting to the checkout. It builds layoutlint for the selected native GOARCH, reuses the existing LLGo compiler and native LLDB, and does not need llgen or lldb-dap. Windows receives the same target-native LLDB Python environment as the existing debugger command. The core caller prepares a temporary module with `.github/test-go.mod/.sum`, runs the action after the ordinary core tests, and removes that copy afterward. Failed checks remain CI failures; only failed/unfinished artifacts and the invocation log are uploaded. Existing matrices, job timeouts and cancellation policies are unchanged.
